# ScamShield Local ML Intelligence Layer

A lightweight, **completely local** ML classifier for suspicious/scam messages.
It classifies a message as `safe` or `scam` using TF-IDF features and a linear
classifier (Logistic Regression). It is an **additional intelligence layer**,
not a replacement for the deterministic message engine
(`src/scamshield/nlp`), which remains the primary, explainable scanner.

> **Research status**: This is a reproducible baseline/research component for
> the ScamShield project. It is **not** state-of-the-art, not a production
> fraud engine, and its confidence values are heuristic estimates - never
> certainty.

## Quick start

```bash
# Train once (from the repo root)
python -m src.scamshield.ml.train

# Predict
python -m app.ml_scan "Your account will be blocked. Verify KYC immediately..."

# In Python
from scamshield.ml import predict_message
result = predict_message("Your KYC has expired. Click the link now.")
```

Predictions work even before training: if no model file is present,
`predict_message` returns a graceful `ML model unavailable` result instead of
crashing.

## Why TF-IDF?

TF-IDF is a simple, sparse, and transparent bag-of-words representation:

- **Sparse & fast**: `TfidfVectorizer` produces a sparse matrix; a linear model
  trains in seconds on a normal laptop with no GPU.
- **Interpretable**: the learned feature weights map directly back to words and
  character n-grams, making the model auditable.
- **Reproducible**: TF-IDF is deterministic and standard, so the baseline is
  easy to re-run and compare against future models.

We combine **word 1-2 grams** with **character 3-5 grams**
(`char_wb`). Character n-grams help with noisy, code-mixed, and
transliterated text (Hinglish / Devanagari) where token boundaries are
uncertain, and they are robust to unseen word spellings. A `FeatureUnion`
merges both views.

## Why a linear classifier?

For a binary high-dimensional (but sparse) TF-IDF feature space, a linear
classifier is the standard, robust choice:

- Logistic Regression is **fast to train and predict**, needs no GPU, and gives
  a well-defined class probability.
- It is far easier to **audit and explain** than a neural model.
- It performs competitively on short text/sparse TF-IDF features.

We use **Logistic Regression** specifically so `predict_proba` is available
(an SVM decision score is *not* a probability; we deliberately avoided Label
the raw score as such). `class_weight="balanced"` partially addresses the
safe↔scam class imbalance.

## Preprocessing

`preprocessing.preprocess()` is a deterministic, stateless pipeline (in this
order):

1. **Unicode normalization** (NFC).
2. **Latin case-folding** - lowercases Latin letters and folds accented Latin
   to ASCII, while **leaving Devanagari intact**.
3. **URL anonymization** - any `http(s)://...` token is replaced with a uniform
   `<URL>` marker (preserves "this message has a link" while not over-fitting
   to a specific host and not persisting raw URLs in features).
4. **Whitespace normalization** (collapse runs, strip ends).

Numbers are **not** stripped because amounts and thresholds (e.g. `50000`,
`Rs.250`) are strong scam signals. The pipeline does **not** do stemming,
lemmatization, POS tagging, or language-specific NLP - it is deliberately
lightweight and does **not** claim full multilingual understanding.

## Dataset: source, size, and suitability

The ML layer uses the **existing ScamShield dataset** (it was found suitable
for binary `scam`/`safe` classification), **not** a newly invented one:

| Split | Raw rows | After dedupe | scam:safe |
|-------|---------|------------|-----------|
| `data/train/messages.csv` | 356 | 285 | 180 : 105 |
| `data/validation/messages.csv` | 88 | 83 | 61 : 22 |
| `data/test/messages.csv` | 110 | 106 | 80 : 26 |

Provenance (see `data/README.md`): `data/raw/ultra_premium_scam_dataset.csv`
is the public HuggingFace `karanverma19/Indian_Multilingual_Scam_Message_Dataset`
(120 rows); `data/processed/messages.csv` (554 rows) combines curated rows from
that dataset (52) with synthetic ScamShield messages (502) generated by
`scripts/build_dataset.py`. All languages: `en`, `hi`, `mr`, `hinglish`.

**Schema** (see `data/schema.md`): `id, text, language, scam_or_safe,
scam_type, source, indicators, split`.

**Suitability decision**: The dataset is suitable for **binary** `scam`/`safe`
classification (`scam_or_safe` is already normalized). The finer-grained
`scam_type` column has **very few examples per category** on this small
dataset (several categories have only ~4-6 rows per split), so we deliberately
**do not** force a multiclass classifier - we preserve `scam_type` as unlearned
metadata only. This matches the requirement to "not force multiclass
classification if the dataset is unsuitable."

**Label validation**: `dataset.validate_labels()` rejects any label not in
`{'scam', 'safe'}` rather than silently relabeling - the pipeline never
invents labels.

## Training pipeline

`python -m src.scamshield.ml.train`:

1. Load train/validation/test splits.
2. Validate schema (required columns) and labels.
3. Remove exact duplicates safely (normalized comparison, keep first).
4. Detect obvious cross-split leakage (reported, not silenced).
5. Build TF-IDF features (word 1-2 + char 3-5 grams).
6. Train Logistic Regression.
7. Evaluate on the validation split.
8. Evaluate the final model on the **frozen test** split.
9. Save the model + evaluation artifacts under `models/`.
10. Print machine-readable metrics.

The model is **trained once** - it is **not** retrained on every prediction.

## Data leakage

The pipeline **detects** leakage between splits and reports it. On the current
dataset, **99 distinct normalized message texts appear in more than one split**
(train/validation/test). This is unsurprising: the synthetic data is generated
from shared templates, so near-identical messages legitimately recur across
splits. Because the frozen test split must not be rebuilt and the source is
template-based, the leakage is **reported honestly** in the console and the
evaluation report rather than silently hidden. Leakage means reported
evaluation numbers are somewhat **optimistic** and the model may not generalize
as well to genuinely novel scam phrasing. See "Limitations."

## Confidence and scores

`predict_message()` returns:

```json
{
  "success": true,
  "model_available": true,
  "prediction": "scam",
  "score": 87,
  "confidence": 87.0,
  "confidence_type": "model_probability",
  "model": "scamshield_ml_tfidf_logreg",
  "features_used": "tfidf_word_char_ngrams",
  "warning": null
}
```

- `prediction`: `"scam"` or `"safe"`.
- `score`: 0-100 integer derived from the predicted-class probability.
- `confidence`: the model's predicted-class probability (0-100 scale).
- `confidence_type`: `"model_probability"` for Logistic Regression (or
  `"normalized_decision_score"` and an explicit NOT-a-probability warning if a
  non-`predict_proba` classifier is ever used).
- `warning`: the honest caveat that confidence is a heuristic model estimate,
  **not** a calibrated, safety-certified probability.

No calibration is implemented - we label the value accordingly and **never
present model/heuristic confidence as certainty**.

## Evaluation

Metrics are computed on both validation and test splits and saved to:

- `models/metrics.json` (machine-readable)
- `models/evaluation_report.md` (human-readable)

For each split we report: accuracy, precision, recall, F1, the confusion
matrix, sample count, and class distribution. We **explicitly discuss both
error directions**, not just accuracy:

- **False negatives** (scam predicted safe): the higher-risk error - a missed
  threat that can lead a user to fall for the scam.
- **False positives** (safe predicted scam): hurts trust and causes user
  friction/annoyance.

Because the dataset is class-imbalanced, accuracy alone is misleading - we
headline precision/recall/F1 and the confusion matrix.

## Unified analyzer integration

`src/scamshield/analyzer.py::analyze("message", ...)` now runs the ML model
alongside the deterministic message engine and exposes the result under
`engine_results["ml_analysis"]`, while the full deterministic result stays
under `engine_results["message"]`:

```text
engine_results:
    message:     { ... deterministic rule result (is_scam, risk_score, ...) ... }
    ml_analysis: { prediction, score, confidence, confidence_type, ... }
```

**Integration strategy**: the deterministic rule score and the ML score are
kept as **separate evidence - they are never averaged or blindly blended**.
The unified top-level `risk_score`, `risk_level`, `is_suspicious` and
`scam_type` remain **driven entirely by the deterministic rule engine** so a
weak or unavailable ML prediction can never hide a real security signal.
If the model is missing, `analyze` still succeeds and `ml_analysis` reports
`model_available: False` - the deterministic result is unaffected. The ML model
path is resolved relative to the repository (not the CWD), so the integration
works regardless of where the process is started.

## CLI


## Model persistence & Git

Trained artifacts are written to `models/`:

- `models/scamshield_tfidf.joblib` - the model bundle
  (`{vectorizer, classifier, meta}`)
- `models/metrics.json` - machine-readable metrics
- `models/evaluation_report.md` - human-readable report
- `models/README.md` - documentation

The `.joblib` model files are **git-ignored** (`models/*.joblib`, `models/*.pkl`,
`models/*.pt`) because they are binary/generated artifacts; metrics and
documentation are plain text and can be committed. The current model is only
~150 KB and small enough to share if desired, but it is intentionally not
tracked to keep the repo clean.

**Security note**: the model file is treated as a local, untrusted artifact.
It is only ever loaded from the local filesystem (never fetched), and the
loaded object is structure-checked (must be a dict exposing `vectorizer` and
`classifier`). A missing or corrupt model degrades gracefully to
"ML model unavailable."

## Security posture

The ML system is **completely offline**:

- no network calls, no URL opening, no DNS resolution, no downloads
- message content is never sent anywhere
- no external APIs, no API keys
- no execution of message contents or attachments
- no credentials logged
- fully deterministic predictions (identical input -> identical output)

## Limitations (honest)

- **Small synthetic dataset**: only ~285 train rows after dedupe; the model has
  limited exposure to real-world scam variability.
- **Class imbalance**: safe messages are the minority; we mitigate with
  `class_weight="balanced"` but the imbalance and the confusion matrix must be
  read together.
- **Cross-split leakage**: 99 shared texts across splits - evaluation numbers
  are somewhat optimistic.
- **Multilingual limits**: preprocessing is lightweight and does **not** deliver
  true multilingual semantic understanding; Devanagari is preserved but the
  model mostly learns surface patterns. Performance on unseen regional phrasing
  will vary, and a safe Hinglish/Hindi message can be misclassified as scam
  (a false positive).
- **No calibration**: confidence is the raw model probability, not a calibrated
  estimate, and is labelled as such.
- **Rules vs ML**: the deterministic engine (rules, keyword/phrase/link
  heuristics, exact explanations) and the ML model (statistical pattern
  matching) are complementary. Rules give explainable, deterministic verdicts;
  ML can capture patterns rules may miss but gives no guarantee and no
  per-pattern explanation. Neither is treated as state-of-the-art; this is a
  reproducibility baseline for the research project.

## Do not claim

This is **not** a production anti-fraud system, not state-of-the-art, and its
confidence values are **not** calibrated probabilities. It is a **reproducible
baseline / research component** that complements the deterministic engines.
